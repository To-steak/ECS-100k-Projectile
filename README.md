# ECS 100k Projectile

Entity Component System을 사용해 씬에 100,000개의 발사체와 2,000개의 피격체가 존재할 때, 충돌 방식에 따른 성능 차이를 측정한 프로젝트입니다.

처음 목표는 직접 생각한 비트 배열 필터가 유효한지 확인하는 것이었습니다.

측정 결과 비트 필터의 성능 기여는 확인되지 않았고, BEST와 BIT의 성능 차이는 주로 격자 조회 방식에서 나타났습니다.

## 비교한 세 가지 방식

1. WORST: 씬 내 모든 발사체와 피격체를 이중 반복문으로 충돌 검사합니다.
2. BEST: 씬을 격자로 분할해 `NativeParallelMultiHashMap`에 저장하고, 발사체 근처 9개(3×3) 격자만 검사합니다. 같은 키의 값들은 `TryGetFirstValue` / `TryGetNextValue`로 순회합니다.
3. BIT: 씬을 격자로 분할하되 격자 인덱스로 정렬해 같은 격자의 피격체를 `NativeArray` 상에 연속 배치하고, 격자별 offset과 count로 구간을 순회합니다.

세 방식 모두 `[BurstCompile]`을 적용한 동일 조건에서 측정했습니다. 충돌 판정은 발사체와 피격체 반지름의 합(1.0)을 기준으로 한 거리 비교이며 `math.distancesq`를 사용해 제곱근 연산을 생략했습니다.

## 측정 환경

- CPU: 12th Gen Intel(R) Core(TM) i5-12600KF (3.70 GHz)
- GPU: NVIDIA GeForce RTX 3060 Ti
- RAM: 16.0GB

개발 빌드에 Profiler를 연결해 측정했습니다. 

fps는 Profiler의 `PlayerLoop` 구간을 환산한 값(`1000 / PlayerLoop`)이며 Profiler 오버헤드가 포함되어 릴리즈 빌드보다 낮게 나옵니다.

각 값은 발사체가 균일하게 퍼진 뒤의 단일 프레임 스냅샷입니다.

동일 코드를 다른 세션에서 두 번 측정했을 때 조회 구간이 약 5% 변동했습니다. 이보다 작은 차이는 유의미하지 않은 것으로 봅니다.

## 결과

`CELL_SIZE = 10`, 피격체 2,000 기준입니다. BIT는 비트 필터를 제거한 상태입니다.

| 방법 | PlayerLoop | fps | 조회 구간 |
|:---|---:|---:|---:|
| WORST | 218.91ms | 4.6 | — |
| BEST | 13.70ms | 73 | 6.39ms |
| BIT | 9.82ms | 102 | 2.26ms |

BEST와 BIT의 시간 차이는 주로 격자 조회 구간에서 나타났습니다.

## 비트 배열의 성능 기여를 확인하지 못함

HashMap 조회 전에 격자별 피격체 존재 여부를 `NativeBitArray`로 확인하면, 피격체가 없는 셀에 대한 조회를 건너뛸 수 있을 것으로 예상했습니다.

| BIT 조회 구간 | BIT 필터 OFF | BIT 필터 ON |
|:---|---:|---:|
| Query | 2.26ms | 2.36ms |

Filter ON에서는 Query가 오히려 0.10ms 증가했습니다. 증가율은 약 4.4%로, 동일 코드를 다른 세션에서 측정했을 때 확인한 약 5%의 변동 범위보다 작았습니다.

따라서 이번 측정에서는 비트 필터를 추가했음에도 Query 시간의 유의미한 감소가 관측되지 않았습니다.

비트 필터는 `USE_BIT_FILTER` 상수로 남겨, 두 상태를 모두 측정할 수 있게 두었습니다.

## 격자 크기에 따른 차이

sparse(BEST) : 피격체가 있는 칸만 저장하는 방식(`NativeParallelMultiHashMap`)

dense(BIT) : 격자 전체를 배열로 잡는 방식(`NativeArray`, 크기 = `TOTAL_CELLS`)

커버 범위(2,000 유닛)를 유지한 채 `CELL_SIZE`를 바꿔가며 측정했습니다.

| CELL_SIZE | 격자 수 | BEST | BIT |
|:---|---:|---:|---:|
| 10 | 40,000 | 73 fps | 102 fps |
| 1 | 4,000,000 | 76 fps | 52 fps |

BEST는 격자 크기에 따른 성능 차이가 크지 않았습니다.

조회 구간은 6.39ms에서 6.07ms로 약 5% 감소했으며, 사전에 확인한 재현 오차 수준이었습니다.

피격체가 있는 격자만 NativeParallelMultiHashMap에 저장하는 sparse 구조라 TOTAL_CELLS 증가에 따른 offset/count 배열의 크기 증가가 없습니다.

단, BIT는 크게 떨어졌는데 늘어난 내역은 다음과 같습니다.

| BIT 단계 | CELL 10 | CELL 1 | 증가 |
|:---|---:|---:|---:|
| 할당 | 0.028ms | 4.48ms | ×160 |
| 초기화 | 0.005ms | 1.61ms | ×322 |
| 정렬 | 0.076ms | 0.076ms | ×1 |
| 조회 | 2.26ms | 3.31ms | ×1.5 |

늘어난 시간의 대부분이 할당과 초기화입니다.

dense 구조라 `TOTAL_CELLS`만큼 배열을 매 프레임 잡아야 하는데, 격자가 100배가 되면서 `gridOffsets`와 `gridCounts`만 합쳐 매 프레임 32MB(4,000,000 × int × 2)를 Allocator.Temp로 할당합니다. 

할당 구간은 4.48ms, 초기화 구간은 1.61ms로 약 2.8배 차이가 났습니다.

## 한계

측정 방식 : 각 값은 단일 프레임 스냅샷입니다. 동일 코드의 재현 오차가 약 5%로 확인되었으므로, 그보다 작은 차이는 판단 근거로 쓰지 않았습니다. 여러 프레임의 중앙값으로 다시 재는 것이 정확합니다.

최근접 선택 미구현 : 판정 반경 안에 피격체가 둘 이상이면 가장 가까운 쪽이 아니라 순회에서 먼저 발견된 쪽이 처리됩니다. BEST에서는 `TryGetFirstValue`가 주는 순서, BIT에서는 배열 정렬 순서를 따르며, 둘 다 발사체와의 거리와는 무관합니다. 최근접을 보장하려면 조기 종료(`break`)를 포기하고 9개 격자를 모두 순회해야 하므로 느려집니다. 성능 비교가 목적이라 세 방식에 동일한 규칙을 적용했습니다.

3×3 순회 시작 위치 : 이중 for문이 `(-1, -1)`부터 시작해 자기 격자 `(0, 0)`을 나중에 봅니다. 자기 격자부터 보면 조기 종료가 더 빨리 걸릴 가능성이 있으나 측정하지 않았습니다.

매 프레임 전체 재구축 : 발사체와 피격체가 계속 이동하므로 격자를 프레임마다 처음부터 다시 만듭니다. 이동량이 작다면 증분 갱신으로 줄일 여지가 있으나 측정하지 않았습니다.

## 개선점

- 여러 프레임의 중앙값으로 재측정 (Profile Analyzer)
- `EntityCommandBuffer.Playback` 차이의 원인 확인. 프레임당 파괴 엔티티 수 계측 필요
- 매 프레임 할당을 피하기 위해 격자 배열을 영속 할당으로 전환했을 때의 차이
- `CELL_SIZE` 2 / 5 구간을 측정해 BEST와 BIT의 교차점 확인
- 3×3 순회를 `(0, 0)`부터 시작했을 때의 차이
- QuadTree 등 불균등 분할과의 비교. 현재 분포가 균일하고 매 프레임 재구축이 필요해 균일 격자를 택했으나, 구현해 재본 것은 아님
